# Реструктуризация истории

Цель: вместо N исходных коммитов — набор атомарных коммитов, где каждый промежуточный коммит собирается и проходит тесты, а вершина побайтово равна исходному состоянию ветки.

Группируй по **финальному** diff ветки, а не по исходным коммитам: при churn исходные коммиты не отражают итог, и перенос их границ воспроизводит мусорную историю.

# Пошаговый порядок

1. Создай backup-ветку: `git branch backup/<имя-ветки>-pre-restructure HEAD`. Это точка возврата до любых деструктивных операций — без неё не начинай.
2. Изучи итоговые изменения: `git diff <base>...HEAD --stat` и `--name-status`. Разбей по библиотекам и областям в порядке графа зависимостей (см. AGENTS.md проекта: stv → karavan → kraslibs → board → configuration_with_gui → docs).
3. **Проверь обратные зависимости на базовой ревизии** — это определяет порядок групп. Для каждого изменяемого публичного заголовка узнай, кто его включает на `<base>`:
   `git grep -l "<заголовок>" <base> -- board/ configuration_with_gui/ karavan/ kraslibs/`
   - Потребитель на `<base>` ещё не адаптирован к ломающему изменению → ломающий коммит идёт ПОСЛЕ коммита-адаптации потребителя.
   - Один файл несёт изменения разных коммитов → раздели файл: восстанови версию с `<base>` (`git show <base>:<файл> > <файл>`), внеси итоговый блок рано, а остальное оставь на поздний коммит. Проверенный паттерн: константа/добавление — ранним коммитом, удаление интерфейса — вместе с адаптацией последнего потребителя.
4. Сбрось ветку на базу с сохранением рабочего дерева: `git reset --mixed <base>`. Дерево = итоговое состояние.
5. Фиксируй группы по одной: в stage — `git add` группы, сообщение — через skill `git-committing-russian`. Перед каждым коммитом проверяй `git diff --cached --stat`, чтобы в группу не попало лишнего.
6. Прогоняй `python3 tools/verify_commit_range.py <base>..HEAD` (собирает каждый коммит диапазона в отдельном worktree и стопается на первом упавшем с сохранением worktree для диагностики). Упавший коммит — сигнал нарушения порядка на шаге 3: вернись, раздели группу или переставь её, начиная со сброса `--mixed` на последний хороший коммит.
7. Финальная сверка: `git diff backup/<имя> HEAD` пуст, `git status` чист.

# Готовность (все условия обязательны)

- backup-ветка создана и сохраняется до успешного слияния;
- порядок групп подтверждён проверкой обратных зависимостей на `<base>`;
- `verify_commit_range` прошёл на всём диапазоне (если сознательно пропущен — скажи об этом явно);
- вершина побайтово равна backup-ветке.

# Частые ошибки

- План по исходным коммитам вместо финального diff → churn переносится в новую историю.
- Проверка включений на финальной ревизии вместо базовой → потребители, которые ещё не адаптированы, обнаруживаются только падением сборки.
- Частая ошибка git: `git diff <ref> --stat` (опции до путей и ревизий после `--`): правильно `git diff --stat <ref> -- <пути>`.
- Не заметить, что pre-commit хук lefthook запускает clang-format на staged-файлах: если финальная сверка с backup не сходится, причина — автоформатирование.
