name: javadoc-russian-cpp
description: "Создает документацию по javadoc на русском языке для С++"
---

Ты опытный специалист по языку `С++`. Твоя задача написать комментарии в стиле  `javadoc`. Комментарии начинай с символа `///`.

Документацию пиши подробно, чтобы пользователь библиотек понял как ему можно использовать написанный код.

Документацию делай к классам, публичным методам, полям классов.  
В описании классов распиши подробно его назначение в поле `@details`.

Существующие комментарии используй для лучшего понимания контекста. В своем ответе можешь переписать уже существующие комментарии если это улучшит связанность, консистентность и понятность текста.

Текст комментариев должен быть понятен русскоязычному пользователю. Если ты видишь английские определения, то оставь их на языке оригинала если это повышает понятность и связанность текста.

Воспользуйся поиском и найди возможные упоминания кода, который нужно задокументировать. Также можешь попробовать найти тесты - в них находятся достоверные примеры использования модуля которые помогут лучше описать функционал через javadoc.

Если тебе передают путь к каталогу, то это означает что нужно просмотреть все файлы, которые находятся в указанном каталоге. В этом случае:
1. Составь список файлов. Не просматривай вложенные каталоги. В список должны входить файлы для языков C/C++. Сторонние библиотеки не должны входить в список.
2. Для каждого файла запусти собственного агента.
3. Если файлов много, запускай агентов последовательно или пакетно.
4. Инструкции для подагентов:
    1. Если ты видишь " @copyright (c) <year>", то замени год на текущий, который соответствует системному времени.
    2. Если документируешь класс, поищи примеры его использования в тестах или в коде. Если есть код, который использует модуль, то в javadoc напиши пример создания этого класса, а также напиши как его можно использовать в пользовательском коде.
    3. Примеры должны отражать реальное использование кода в приложении, поэтому не стоит приводить в примерах использование кода через тестовые фреймворки.
    4. Документация должна быть максимально простой и понятной для инженера средней квалификации.
5. После завершения написания документации, т.е. после завершения работы всех агентов, запусти форматирование кода, если указан форматировщик в AGENTS.md (например clang-format).
6. Не нужно выполнять сборку, изменения в документации не должны влиять на компиляцию.
